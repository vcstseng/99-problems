DEV09AI-Native Development

Should an AI-generated change be allowed to deploy itself all the way to production?

As AI increases change volume, organizations need risk-based release authority instead of either full autonomy or manual approval for everything.

01

What's the problem?

As AI increases change volume, organizations need risk-based release authority instead of either full autonomy or manual approval for everything.

02

What do we need to know?

Use change intent, dependencies, risk classification, test and security evidence, SLOs, error budgets, production telemetry, and rollback capability.

Key inputs

Code changes, change intent, dependencies, risk classification, test/security evidence, SLO/error budget, production telemetry, rollback data

Existing systems

Git, CI/CD, feature flags, observability, deployment platform

03

What does AI change?

AI can classify change risk and summarize evidence, while release safety still depends on CI/CD, canaries, feature flags, SLOs, and rollback controls.

04

How do we solve it?

Set the maximum release authority by risk tier—PR, merge, staging, canary, or production—and use progressive delivery to limit blast radius.

Solution Core

Risk-Based Release Authority + Change Risk Classification + CI/CD Gates + Progressive Delivery

05

What does AI do?

Assess change risk and assemble release evidence for policy gates.

06

What do people decide?

Set production risk appetite, mandatory approvals, SLOs, and emergency-release policy.

07

What improves?

Increase release autonomy where evidence supports it without weakening production safety.
