SEC04Security

Once an MCP server, plugin, or skill is installed, how do we know it is still safe after an update?

AI extensions can change code, permissions, dependencies, or network behavior over time, so a component that was safe when installed may become risky later.

01

What's the problem?

AI extensions can change code, permissions, dependencies, or network behavior over time, so a component that was safe when installed may become risky later.

02

What do we need to know?

Maintain an inventory of components, manifests, package provenance, permissions, versions, signatures, network destinations, and dependencies.

Key inputs

Component inventory, MCP/plugin/skill manifests, source/package metadata, permissions, versions, signatures, network destinations, dependency data

Existing systems

Plugin/MCP registry, package registry, IAM, SIEM

03

What does AI change?

AI can help inspect semantic behavior and risky capability changes, but provenance, signing, version pinning, and permission checks should remain deterministic controls.

04

How do we solve it?

Register every component, verify source and signature, pin approved versions, review permissions, and re-check changes before upgrades are allowed.

Solution Core

AI Component Inventory + Provenance/Signature Verification + Version Pinning + Permission Review + Semantic Risk Inspection

05

What does AI do?

Analyze manifests, documentation, and changes for suspicious capability or behavior shifts.

06

What do people decide?

Approve trusted sources, acceptable permissions, and update policy.

07

What improves?

Reduce supply-chain risk from AI components that silently change after deployment.

How does the agent framework approach this problem?

Start with the decision and evidence needs, then combine consulting skills and approved tools under human review, security and governance. The framework defines the approach; this page alone does not establish implemented capability or proven results for this problem.
