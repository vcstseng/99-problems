DEV07 AI 原生開發

每個模組都測試通過，合起來為什麼還是壞？

AI產生或修改的各個模組可能各自符合Local Tests，卻違反跨系統API/Schema Contract、Consumer Expectations或End-to-End Business Behavior，形成Local Success、Global Failure

01

問題是什麼？

AI產生或修改的各個模組可能各自符合Local Tests，卻違反跨系統API/Schema Contract、Consumer Expectations或End-to-End Business Behavior，形成Local Success、Global Failure

02

需要知道什麼？

單一模組 Test 全綠，不代表跨服務整合一定正確。需要 API、Schema、Consumer Expectation、Service Dependency、Integration／E2E Test 與同一批 Change Set，才能知道接口和實際 User Journey 是否一致。

主要資料

APIs、Schemas、Interface Contracts、Consumer Expectations、Integration/E2E Tests、Service Dependencies與Change Sets

既有系統

API Gateway、Git、CI/CD、Service Catalog、Contract Testing Tools

03

AI 改變了什麼？

Contract Testing、Schema Compatibility與End-to-End Testing已是成熟的Deterministic Controls；AI的增量不是取代這些Tests，而是從Requirements與多個Change Sets找出可能的Semantic Mismatch、產生Cross-Component Scenarios並發現Integration Coverage Gaps。

04

怎麼解？

先用 Schema Compatibility 和 Contract Test 檢查可形式化的 Interface，再分析跨 Component 變更找可能的語意衝突與缺漏情境。最後用 Integration／E2E Test 驗證真正重要的端到端流程。

Solution Core

Contract Testing + Schema Compatibility + AI-Assisted Integration Scenario Generation + End-to-End Verification

05

AI 做什麼？

先以Schema與Consumer-Driven Contract Tests驗證可形式化的Interface Compatibility，再由AI分析跨Component Changes與Requirements，提出可能的Semantic Conflicts與Missing Integration Scenarios，最後以Integration/E2E Tests驗證Critical User Journeys

06

人決定什麼？

定義Cross-System Invariants、Authoritative Contracts與Critical User Journeys，判斷Semantic Differences是否屬於真正Defect並決定Release-Blocking Integration Issues

07

最後改善什麼？

降低各模組Local Tests全部通過卻在整體系統產生Integration Failure的風險，讓Cross-System Behavior在Release前得到獨立驗證
