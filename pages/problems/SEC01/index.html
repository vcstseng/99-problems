SEC01 安全

有人能在文件、Email 或網頁裡偷偷下指令控制 AI 嗎？

AI Agent讀取Email、文件、網頁或RAG內容等不可信資料時，可能把其中的惡意或誤導性文字當成Instruction，造成Direct/Indirect Prompt Injection並偏離原本任務

01

問題是什麼？

AI Agent讀取Email、文件、網頁或RAG內容等不可信資料時，可能把其中的惡意或誤導性文字當成Instruction，造成Direct/Indirect Prompt Injection並偏離原本任務

02

需要知道什麼？

要防 Prompt Injection，先要知道 AI 接收到哪些 User Prompt、Email、文件、網頁與 RAG 內容，以及每段內容從哪裡來、是否可信。還要能追到 Agent 後續用了哪些 Tool、做了哪些 Action。

主要資料

User Prompts、Email、Documents、Web Content、RAG Context、Content Provenance、Agent Traces、Tool Calls

既有系統

LLM Gateway、RAG、Email、Browser、DMS

03

AI 改變了什麼？

傳統AppSec可以控制Code、Network與Identity，但Agent同時以自然語言接收Instruction與Data，使不可信內容可能跨越兩者邊界；目前沒有能可靠辨識所有Prompt Injection的語意Filter，因此不能只靠模型判斷內容是否安全。

04

怎麼解？

先把可信指令和不可信內容明確隔離，偵測可疑指令與上下文操控，再限制不可信內容能影響的工具和操作。高影響行為最後交給模型之外的 Policy 或人工核准，避免內容本身取得控制權。

Solution Core

Trusted/Untrusted Context Isolation + Prompt Injection Detection + Least Privilege + Runtime Policy Enforcement

05

AI 做什麼？

標記並隔離Trusted Instructions與Untrusted Content，偵測可疑Instruction與Context Manipulation，限制不可信內容可影響的Tools與Actions，並將高影響操作交由模型之外的Policy或人工Approval控制

06

人決定什麼？

定義Trusted Sources、Agent可使用的資料與Tools、高風險Actions及Approval Policy；對模型無法可靠判斷的情境採取隔離、拒絕或人工確認

07

最後改善什麼？

降低Prompt Injection從不可信內容跨越到敏感資料與高影響Actions的機率，限制成功攻擊後的Blast Radius

這個問題如何透過 Agent Framework 處理？

先釐清決策與證據需求，再組合顧問 Skills 與允許的 Tools，透過人機協作、安全邊界與治理審查形成方案。框架提供共用方法，不代表本題所有能力都已實作或成果已驗證。
