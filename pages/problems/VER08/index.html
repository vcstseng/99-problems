VER08 可靠性與驗證

當 AI 已經不能安全繼續時，系統能不能停下來，不要硬做到底？

當系統已判定Evidence、Tools、Policy條件或Verification不足以安全完成任務時，如果沒有事先設計Safe Degradation Path，Agent仍可能繼續猜測、執行部分Actions或讓Business Process卡在不一致狀態

01

問題是什麼？

當系統已判定Evidence、Tools、Policy條件或Verification不足以安全完成任務時，如果沒有事先設計Safe Degradation Path，Agent仍可能繼續猜測、執行部分Actions或讓Business Process卡在不一致狀態

02

需要知道什麼？

系統要能安全停下來，必須先知道哪些 Verification／Policy Signal 代表不能再繼續，以及當下 Workflow State、Tool 狀態、可用 Fallback 和上一個穩定版本在哪裡。

主要資料

Failure/Verification Signals、Tool Status、Workflow State、Policy Constraints、Fallback Options、Previous Stable Versions與Compensating Actions

既有系統

Agent Platform、Workflow、Policy Engine、Monitoring、Queue/Ticketing

03

AI 改變了什麼？

判斷何時應停止主要由Verification與Governance Signals提供；Reliability的問題是停止後系統如何安全退場。傳統Exception Handling多處理明確Error Code，而AI Workflow還需要針對無法安全完成的情境預先設計Abstain、Read-Only、Deterministic Fallback、Human Queue與State Recovery。

04

怎麼解？

當驗證或治理條件不通過時，不硬做到底，而是依風險切換成 Abstain、Read-only、確定性流程、上一個穩定版本或人工 Queue。已經做出去、不能 Rollback 的 Action，則啟動補償措施。

Solution Core

Graceful Degradation + Abstain + Deterministic Fallback + State Preservation + Compensating Actions

05

AI 做什麼？

當外部Verification或Governance判定不能安全繼續時，依Workflow風險切換為Abstain、Read-Only、Deterministic Process、Previous Stable Version或Human Queue，停止高風險Tool Execution並保存必要State；已執行且無法Rollback的Action則啟動預先設計的Compensating Action

06

人決定什麼？

定義不同Failure Mode的Fallback Priority、允許的Degraded Mode、Emergency Override與Recovery責任，確認哪些Actions可Rollback、哪些只能補償或人工處理

07

最後改善什麼？

讓AI在無法安全完成任務時以可預期方式降級而不是硬完成，降低Partial Execution、不一致State與高影響Failure造成的營運風險
