DEV01 AI 原生開發

AI 寫程式很快，但需求沒寫清楚的地方，它是不是自行決定了？

當Implementation變得極快時，模糊或不完整的需求可能被AI自行補上隱含假設並直接實作；經過多次修改後，這些未經確認的Assumptions還可能讓Code逐步偏離原始Business Intent、Architecture Constraints與Acceptance Criteria

01

問題是什麼？

當Implementation變得極快時，模糊或不完整的需求可能被AI自行補上隱含假設並直接實作；經過多次修改後，這些未經確認的Assumptions還可能讓Code逐步偏離原始Business Intent、Architecture Constraints與Acceptance Criteria

02

需要知道什麼？

AI Coding 最大的風險之一，是需求沒寫清楚時它自己補完。要把 Requirements、User Story、Business Rule、Acceptance Criteria、Architecture Decision、Assumption、Code 與 Test 放在一起，才能看見哪些地方其實沒被明確決定。

主要資料

Requirements、User Stories、Business Rules、Acceptance Criteria、Architecture Decisions、Assumption Register、Code、Tests與Change History

既有系統

Jira、Confluence、Git、ADR/Product Docs

03

AI 改變了什麼？

AI能快速找出Spec Ambiguity、Conflicts與Missing Cases，但也可能自行補完需求空白；可靠控制不是只讓另一個AI比較Spec與Code，而是先把隱含Assumptions明確化，並盡可能將Intent轉成可執行的Acceptance Criteria、BDD、Contracts或Property Tests。

04

怎麼解？

在寫程式前先找出模糊、衝突、Edge Case 和未明說的假設，要求 Agent 把它們列出來，而不是自行選答案。能形式化的需求再轉成 Acceptance Criteria、BDD、Contract 或 Property Test，持續檢查 Code 是否符合。

Solution Core

Assumption Extraction + Executable Specification + Acceptance Criteria + Spec–Code Alignment

05

AI 做什麼？

Coding前找出Requirement中的Ambiguity、Conflicts、Edge Cases與未明說的Assumptions，要求Agent明確列出而非自行決定；將可形式化的Intent轉成Acceptance Criteria、BDD、Contracts或Property Tests，並在後續Changes持續檢查Implementation是否仍符合這些Constraints

06

人決定什麼？

定義真正Business Intent、優先順序與不可自行假設事項，確認重要Assumptions與Acceptance Criteria，核准Intentional Scope/Design Changes並維護Source of Truth

07

最後改善什麼？

降低AI高速實作錯誤假設與Cumulative Intent Drift的風險，讓需求空白在進入Code前被看見並使重要Business Intent具有可驗證的Execution Evidence

這個問題如何透過 Agent Framework 處理？

先釐清決策與證據需求，再組合顧問 Skills 與允許的 Tools，透過人機協作、安全邊界與治理審查形成方案。框架提供共用方法，不代表本題所有能力都已實作或成果已驗證。
