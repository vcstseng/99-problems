DEV04 AI 原生開發

同一個 AI 寫程式又寫測試，全部綠燈真的代表做對了嗎？

AI同時產生Implementation與Tests時可能共享相同錯誤假設；即使改用另一個模型產生Tests，也可能因訓練資料與推理模式相近而形成相關盲點，使全部Tests通過卻沒有真正獨立驗證

01

問題是什麼？

AI同時產生Implementation與Tests時可能共享相同錯誤假設；即使改用另一個模型產生Tests，也可能因訓練資料與推理模式相近而形成相關盲點，使全部Tests通過卻沒有真正獨立驗證

02

需要知道什麼？

同一個 AI 同時寫 Code 和 Test，容易出現兩邊一起誤解需求、最後卻全部綠燈的情況。需要獨立的 Requirements、Human-defined Invariants、Contracts、Historical Bugs、Reference Behavior 與 Held-out Tests。

主要資料

Code、Tests、Requirements、Human-Defined Invariants、Contracts、Historical Bugs、Reference Behavior、Hidden Tests與Mutation Results

既有系統

Git、CI/CD、Test Framework、Mutation Testing Tools

03

AI 改變了什麼？

AI適合大量產生Tests，但不同模型不等於Independent Evidence；更可靠的驗證應來自不同資訊來源，例如Human-Defined Invariants、Executable Specs、Contracts、Existing System Behavior與Held-Out Tests，並用Mutation Testing直接測量Tests是否真的能抓到故意注入的錯誤。

04

怎麼解？

測試證據要盡量獨立於實作本身。用 Property／Contract Tests、Held-out Cases 和歷史 Bug 建立外部檢查，再透過 Mutation Testing 故意注入錯誤，確認現有 Test 真的抓得到問題。

Solution Core

Independent Test Evidence + Mutation Testing + Property/Contract Testing + Deterministic Quality Gates

05

AI 做什麼？

從Requirements、Invariants、Contracts、Historical Bugs與Reference Behavior建立獨立Test Evidence，使用Property/Contract Tests與Held-Out Cases降低Implementation/Test同源風險，並透過Mutation Testing故意注入Faults，檢查現有Tests是否真的能偵測錯誤

06

人決定什麼？

定義Critical Invariants、Authoritative Specifications與不可妥協的Quality Gates，維護不受Implementation Generator控制的Independent/Held-Out Test Evidence

07

最後改善什麼？

降低Code與Tests共享同一錯誤假設卻全部綠燈造成的虛假信心，讓Test Quality本身也能被實際驗證
